Experience Quality Rubric
JBIQ · Core Experience · FnF Release
Front-end consumer experiences only
A two-layer evaluation framework for all user-facing experiences on the JBIQ app. The universal rubric (7 dimensions) is fixed and applies to every use case. Criteria cards are team-owned and define what pass, warn, and fail look like for each specific use case type.
Scope: This rubric applies to front-end consumer-facing experiences only — anything a user sees and touches on the app. Internal systems (APIs, ML models, UCP pipeline, backend infra, eval pipelines) run independently and are not in scope here. They feed into this rubric but are evaluated separately.
What this is
Central — Core Exp

Universal dimensions — fixed for all FE use cases
D1 — Functional behaviourP0 if score = 2
Did the feature do what it was supposed to do for this input on this device?
0 — pass
Feature completed the task as expected. Output matched test criteria.
1 — warn
Feature ran but output was incomplete, inconsistent across retries, or required a workaround.
2 — fail
Feature failed, errored, timed out, or produced no output.
D2 — Output and response qualityP0 if score = 2
Was the output factually correct, relevant, and complete for the user's intent?
0 — pass
Correct, directly addresses query, complete. Matches golden answer where one exists.
1 — warn
Partially correct or relevant. Right intent, minor factual gap or wrong format.
2 — fail
Wrong fact stated confidently. Hallucinated entity or name. Irrelevant answer to a clear query.
D3 — Trust and user experienceP0 if score = 2
Would a real user trust this output and continue using the product?
0 — pass
Output feels confident and safe. User has no reason to doubt the product.
1 — warn
Output felt odd but user could still proceed. Minor friction, trust intact.
2 — fail
Output breaks trust. User would stop, question the product, or abandon the task.
D4 — Language and localisationP0 if score = 2
Was the response in the right language, script, and cultural register?
0 — pass
Right language throughout. Script renders correctly. Phrasing natural for a native speaker.
1 — warn
Right language, minor awkward phrasing or transliteration error. Mixed script in one sentence.
2 — fail
Wrong language. Script garbled or unreadable. Culturally inappropriate or offensive phrasing.
D5 — Visual design and IAP0 if score = 2
Does the UI render correctly, follow the spec, and make sense as an information structure?
0 — pass
Renders correctly on target device. Matches Figma spec. IA clear — user knows where they are and what to do next.
1 — warn
Minor spacing or layout deviation. IA mostly clear but one element confusing. Figma delta is cosmetic only.
2 — fail
Layout broken on target device. Key action hidden or unreachable. IA broken. No Figma spec and build not signed off.
D6 — Voice interaction qualityP0 if score = 2
Did voice input, output, and all interaction states work correctly end to end?
0 — pass
STT transcribes correctly. TTS natural and intelligible. Barge-in works. All states — listening, processing, speaking — visible and correct.
1 — warn
Minor STT inaccuracy. TTS slightly unnatural but intelligible. State feedback delayed but present.
2 — fail
STT fails silently. TTS unintelligible. Barge-in broken. No state feedback shown. Voice loop broken.
Score 0 if use case has no voice component — D6 does not apply and does not inflate the total.
D7 — Flow and reachAmplifier only — cannot trigger P0
Where in the user journey does this happen and how many users are affected?
0 — pass
Edge case or low-frequency path. Most users unaffected.
1 — warn
Secondary flow. A subset of users on a specific path would hit this.
2 — fail
Core flow. Most users attempting this task would encounter it.
D7 amplifies the total score but cannot trigger P0 on its own. A cosmetic issue in a core flow is still P2, not P0.

D5 expanded — design evaluation criteria
Design evaluation covers six layers within D5. The most important gate is whether a Figma spec exists and is signed off. Without it, D5 is inconclusive and the use case cannot ship. Visual expression feasibility is a pre-development check — not a QA finding.
Design layer What QA checks Pass Warn Fail Severity
Figma spec Is there a signed-off Figma file to evaluate against? Figma spec exists, signed off by Matt or Sunit. Spec exists but not signed off. Treat as provisional — flag to leads. No spec. Build made on the fly with no sign-off. D5 = inconclusive. Cannot ship without explicit risk acceptance. P0
Spacing and padding Does spacing match JDS tokens on target device? No unintended crowding or overflow? Spacing matches JDS tokens. No overflow. Comfortable on ₹7K device screen. 1–2 elements with minor spacing deviation. Doesn't affect readability. Content overflowing container. Text touching edges. Unusable on minimum target device. P1
Information architecture Can the user orient, navigate, and understand hierarchy at a glance? Clear hierarchy. Primary action obvious. User knows where they are and what to do next. Hierarchy mostly clear but one section ambiguous or competing with another. User cannot tell what to do next. Primary action buried. Multiple competing focal points. P0
Typography and readability Is text readable on target devices in all supported languages? Font size legible on minimum target device. All scripts render. Line height comfortable. Slightly small on one device. One script slightly cramped but readable. Text unreadable on target device. Script not rendering. Font missing characters for a supported language. P0
Component fidelity Do built components match the Figma spec in colour, shape, and interaction states? Components match spec. JDS tokens applied correctly. All states — default, pressed, disabled — present. Minor colour or radius deviation. One interaction state missing but flow works. Component visually unrecognisable from spec. JDS tokens not applied. Key state missing. P1
Visual expression feasibility Is what was designed in Figma actually achievable in the tech stack on target devices? All visual expressions in spec are achievable and implemented correctly. One visual expression approximated — looks close but not exact. Logged with Matt. Visual expression in Figma is not achievable in current stack. No fallback defined. Ships broken. P0
Visual expression feasibility check must happen before development starts — not at QA. If a Figma component cannot be built as designed on target devices, that is a design–engineering conversation during sprint planning. Matt owns this check. If it reaches QA as a broken visual, it is already too late and costs a sprint.
D6 expanded — full voice interaction evaluation
Voice evaluation must be run per language. STT and TTS quality differs significantly across Hindi, Tamil, Bengali, and other FnF target languages. Passing on one language does not cover others. D6 scores 0 for all non-voice use cases.
Voice layer What QA checks Pass Warn Fail Severity
Mic activation Does the mic activate on tap? Is activation feedback immediate? Mic activates within 200ms. Visual feedback — waveform or indicator — appears immediately. Mic activates but feedback delayed 500ms+. User unsure if it registered. Mic does not activate. No feedback. Silent failure with no error state. P0
STT — speech to text Does transcription accurately capture spoken input in the target language? Transcription matches spoken input. Word error rate within threshold. Intent preserved. Minor word-level error. Intent preserved but one word wrong. Transcription so wrong intent is lost. Fails on target language. Silent failure. P0
TTS — text to speech Is synthesised voice output natural, intelligible, and in the right language? TTS natural and intelligible. Language correct. Pronunciation acceptable for target audience. Slightly robotic but intelligible. One word mispronounced but not misleading. TTS unintelligible. Wrong language. Mispronunciation changes meaning. P0
Barge-in Can the user interrupt TTS playback by speaking? Does it stop and listen correctly? Barge-in works reliably. TTS stops within 300ms. System switches to listening state. Barge-in works but has 500ms+ lag. TTS takes a moment to stop. Barge-in not working. TTS continues over user speech. User has to wait or tap to stop. P0
Listening state Is it clear to the user that the system is actively listening? Listening state clearly indicated — waveform, animation, or label. Duration feels comfortable. Listening indicator present but subtle. User may not notice. No listening indicator. User cannot tell if system is ready. Listening times out with no feedback. P0
Silence detection Does the system correctly detect end of speech and stop listening at the right moment? End-of-speech detection accurate. No premature cutoff. No excessive wait after user stops. Fires slightly early — last word occasionally cut. Or waits 1–2s longer than expected. Cuts user off mid-sentence consistently. Or never detects end of speech — user has to tap to stop. P1
Processing state Is there visual feedback while the system processes the voice input? Processing indicator shown between end of listening and start of response. No blank gap. Processing indicator shown but disappears before response loads — brief blank gap. No processing indicator. Blank screen between listening and response. User thinks system failed. P1
Error recovery When voice fails — mic error, STT failure, network drop — does the user get a clear recovery path? Error state shown clearly. User offered to retry or switch to text. No dead end. Error state shown but recovery path not obvious. User has to figure out next step. Silent failure. No error state. No recovery path. User is stuck with no exit. P0
Double-trigger prevention Does the system prevent accidental double-activation of the mic by TTS output? No double-trigger. Mic deactivates correctly after response. TTS output does not trigger mic. Rare double-trigger in specific conditions. Reproducible but infrequent. TTS output triggers mic. Consistent double-trigger. Endless loop possible. P0
How QA runs this for any use case — 8 steps
1
Identify the use case type
Determine which of the five use case types this test covers — skill response, onboarding, homepage, voice, or language. If it spans more than one, split into separate test runs.
Output: use case type confirmed
2
Pull the signed criteria card
Get the team's criteria card for that use case type. If no signed card exists — stop. Raise it as a process blocker. Do not start testing until the card is signed off by the owner.
Output: criteria card in hand
3
Run the test input
Execute the test against a known input — ideally from the golden dataset. Record exact output. For voice: capture the transcription. For UI: record tap sequence and screenshot.
Output: raw output captured
4
Score each dimension D1–D7
Score each dimension 0, 1, or 2 using the criteria card. Write the reason in one sentence per dimension — not a judgment, an observation. "D2 scored 2 because the response stated the wrong match score against the golden answer."
Output: 7 scores + 7 reasons
5
Check P0 override immediately
If any of D1, D2, D3, D4, D5, or D6 scores 2 — it is P0 regardless of total. Do not wait to add up the score. Flag immediately.
Output: P0 confirmed or ruled out
6
Add up total and assign priority
Sum D1–D7. Apply scoring table: 9–14 = P0 · 6–8 = P1 · 3–5 = P2 · 0–2 = P3. For non-voice use cases D6 = 0 automatically.
Output: priority assigned
7
Log in ADO
If P0 or P1: raise a bug with score breakdown, reason per dimension, use case type, and owner. If P2/P3: add to backlog with score. A bug without a score breakdown is returned to the logger.
Output: ADO ticket created
8
Set use case verdict
If any P0 open → use case does not work. If only P1/P2 open → works with known issues. Zero issues → works. Inconclusive if test could not complete.
Output: use case verdict confirmed
