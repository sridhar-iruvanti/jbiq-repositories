JBIQ — Domain × Persona Architecture

Author: Sridhar

Part A: The Architecture

1. Foundations

1.1 What JBIQ Is Built On

JBIQ is built for five specific people — Arjun, Priya, Ramesh, Sunita, Raju. Not user archetypes. Not segments. Five people with specific lives, languages, aspirations, and constraints that no generic AI is designed for.

Three things make JBIQ structurally different from any other AI assistant:
Jio ecosystem access Proprietary data and integrations — JioCinema, JioMart, OCP, Jio location signals — that no competitor can replicate. This is what makes a signature experience possible.
Omni Central Profile (OCP) The single user-level data store — periodically processed, stored in BigTable. Fed by 3 producers: UCP (Jio ecosystem subscriber data) · App events (user behaviour and app data — onboarding inputs, Google Analytics, Clevertap) · Conversational Memory (what JBIQ has learned, transformed to profile level). Personalisation runs on this as its base — surfacing the right experience at cohort or user level.
Language as existence, not localisation Gujarati for Sunita is not a translated version of the Hindi product. If it is not in Gujarati, she will not use it. This applies to every Segment C/D user in a non-Hindi state.

1.2 What a Domain Is

A domain is a bounded part of a user's life where JBIQ needs to show up as a fundamentally different kind of AI. The same person checking cricket scores, looking for a govt scheme, and processing a life decision is in three completely different intent states. One AI character cannot serve all three well.

A topic becomes a domain only when it passes all three:

Question Why it matters
Does it need its own AI persona — different character, tone, knowledge depth? Cricket Buddy and Saathi cannot be the same persona. The register, emotional contract, and depth are fundamentally different.
Does it have ≥1 signature experience with a named proprietary source? Without a source no competitor can replicate, it's use cases any AI can handle — not a domain with a moat.
Is the user in a genuinely different intent state? Inform me · Decide · Transact · Feel heard · Get what I'm owed. These are different people in different moments.

All three yes → domain. Any no → fold into a broader domain or treat as everyday use cases within one.

What alone does not make a domain: a content feed · a feature · a topic without a proprietary source · a team's ownership scope

3. How a Domain Gets Built

3.1 The Architecture

Every query flows through a pipeline: pre-flight (guardrails + memory load) → skill discovery (RAG retrieval) → coordinator (reasoning + tool execution) → output (response + memory write).

The one thing that matters for domain building: Skills are retrieved per query, not preloaded. The Coordinator gets the domain skill only when the query routes to it. Each domain skill declares how it runs — via one of three execution modes:

Mode What it means Used when
persona_prompt Domain character added to system prompt. No tool calls. Answering from LLM knowledge — everyday use cases
mcp_tools Domain tool schemas injected. APIs fire in parallel. Fetching live proprietary data — signature experiences
agent_as_tool Isolated specialist subagent. Complex multi-step workflows. End-to-end flows needing their own reasoning loop

The mode determines whether a use case is everyday or signature. persona_prompt = any AI can do it. mcp_tools or agent_as_tool on a proprietary integration = only JBIQ can do it.

3.2 The 7 Primitives

Every response is a combination of primitives. The domain and user profile determine which ones fire and in what proportion.

Primitive What it is Rule
Voice Output TTS in user's language Standalone-complete — meaningful without the screen
Text Response Short structured text on screen Mirrors or extends voice
Rich Card Image + title + 1–2 lines + CTA Used for content, products, jobs
Action JBIQ does something — adds to cart, books, sets alert, places order Closes the loop within the conversation
Clarification Single follow-up question Never more than one in a row
Next Step Post-task suggestion Keeps the conversation going — the primary re-engagement mechanism
Navigation Move user to domain page or deeper context Taps connect chat to surface

Three drivers determine which primitives fire: query complexity · domain · user profile (voice-first vs text, low literacy vs fluent).

3.3 Worked Example — Cricket Domain

Query: "Aaj ka match kaun jeeta? Fantasy mein kya karna chahiye?"

Pre-flight      →  Memory loads: fantasy team composition (OCP)
                   Language: Hinglish detected

Skill Discovery →  Cricket skill retrieved
                   Execution mode: mcp_tools

Coordinator     →  Fires 2 tools in parallel:
                   [1] JioCinema live API  → match result + scorecard
                   [2] Fantasy platform API → team impact delta

Output          →  Voice: "Mumbai Indians jeet gaye — 6 wicket se."
                   Text: Scorecard + turning point
                   Rich Card: Rohit 82* — your captain delivered
                   Next Step: "3 transfers suggest kar sakta hoon — dekhein?"
                   Memory write: match result + fantasy check stored

Without the live integration → score lookup, any AI can do it. With JioCinema + fantasy API → actual team impact in one response. The tool call is the moat.

Same query, different user profile — how primitives shift:

Primitive Voice-first, low literacy Text input, digitally fluent
Voice Output "Aaj Mumbai Indians ne 6 wicket se jeeta" —
Text Response Score card — minimal, large text Full scorecard + innings breakdown
Rich Card — Rohit Sharma 82* — top performer
Next Step "Kal ka match bhi dekhein?" "Fantasy impact check? 3 transfers suggest kar sakta hoon."
Action — [Set alert for next match]

3.4 The N=1 Arc

Know You        Sessions 1–5     OCP loaded at pre-flight.
                                 Language, context, cohort defaults set.
                                 JBIQ feels built for you from Turn 1.

Remember You    Sessions 6–20    In-app behaviour fills in the person.
                                 Fantasy team. GSTIN. Gotra.
                                 JBIQ stops using the archetype, starts using the person.

Anticipate You  Sessions 20+     Individual model fully active.
                                 JBIQ knows you check scores at lunch.
                                 Delivers before you ask.
                                 No competitor can replicate a 20-session relationship.

3.5 What Every Domain Needs to Be Specced As

1. Skill manifest
   → execution mode: persona_prompt / mcp_tools / agent_as_tool
   → character · tone · register · never-does

2. Safety rules (domain-specific)
   → Health: never diagnose
   → News: never editorialise
   → Astrology: never over-promise
   → Finance: numbers only, no investment advice

3. Tool list
   → which proprietary APIs · what they return · what triggers them
   → no proprietary tool = no signature = no moat

4. Memory schema (OCP)
   → what gets stored per session
   → what gets loaded at pre-flight · what gets written at output

5. Primitive templates
   → which primitives fire for this domain
   → how they combine per user profile

5. Signature Experience Framework

5.1 The 3 Bars

A signature experience must clear all three bars. Missing any one = everyday use case.

Bar What it means What it rules out
1. Proprietary access Jio ecosystem data, exclusive partnership, or strategic integration no competitor can replicate Generic web APIs, public data sources, anything ChatGPT can also call
2. Solves what AI + web search can't The combination of LLM + this integration solves a problem that ChatGPT + Google fundamentally cannot Anything achievable by "ask ChatGPT + search it"
3. Intrinsic pull Creates a habit or experience so compelling the user returns without a PN or WhatsApp trigger Anything that only works as a push — no notification = no return 
Use Cases
  The full set of what users come to this domain to do.
  Frequency is the nature of the use case — not a separate category.
  Any well-built AI could do this.

Signature Experiences
  What only JBIQ can uniquely deliver through proprietary access.
  Often proactive — JBIQ delivers without the user needing to ask.
  Must meet all 3 bars. Requires a proprietary tool call. This is the moat.

Part B: The Personas

6. Why the Same Domain Is a Different Product

The domain sets the character. The user profile — loaded from OCP at pre-flight — shifts the register: language, format, tone, primitives, what gets stored.

Consider Devotion:

Sunita Priya
What she needs Daily Gujarati ritual, correct tithi, gotra-personalised — her core identity A way to do something meaningful for parents far away — gifter, proxy
Magic moment Aashirvaad in Gujarati with her name and gotra. She would not use it in Hindi. Somnath prasad delivered to her mother-in-law. Goes on 34-person family WhatsApp.
Register Devotional, deeply personal, automated daily habit Warm, gifter-framing, delivery tracking
Memory needed Gotra, daily ritual time, tithi preference Mother's address, festival calendar, past prasad orders

Same domain. Completely different product. One register and one memory schema built for one will fail the other.

10. Decision Making

10.1 Where Complexity Lives

Layer Complexity Why
Signature experience integrations High Each needs a distinct integration — JioMart API, NCS portal, JioCinema, health memory schema. Each is a dependency.
Register adaptation (N=1) High Requires memory architecture, not just prompt variation. Cannot be faked with persona switching.
Domain knowledge tuning Medium Retrieval and context — domain-specific, not model training
Primitive rendering Medium Shared infrastructure, domain-specific templates

10.2 Hard Cells — Where Integration Must Be Live

Cell Why it's hard What happens without it
Raju × Devotion Requires Bhojpuri/Maithili content library — not Hindi translation Signature collapses to everyday use case
Arjun × Cricket JioCinema integration must be real in-thread action Without it, it's just a score lookup — any app does that
Sunita × Health Longitudinal memory requires health schema in OCP Without it, Health Buddy has no signature — just symptom lookup
Ramesh × Government Services GSTIN auto-link must connect to actual scheme application — not just show eligibility Without proof, Ramesh dismisses it as a kagzi scheme
Priya × Finance Home loan parameters must be stored in OCP — not re-entered every time Without it, every session starts from scratch — just a generic EMI calculator

10.3 Trust Architecture

Principle In practice
Show, don't prove Trust is built through the quality of the response, not a privacy disclosure. Every accurate, well-timed answer is an act of trust.
Inference is not fact The model acts on inferences silently. It never states a conclusion as though the user confirmed it.
Memory is a relationship Remembered context is a feature. How it is surfaced — and how it can be removed — defines the relationship. Memory that cannot be controlled cannot be trusted.
Explainability builds trust When the assistant does something unexpected, the user should understand why. Transparency is a design decision, not a compliance requirement.

10.4 The 3 Non-Negotiables

1. Language is the product for Sunita — not localisation, existence. If it's not in Gujarati, she won't use it. A Hindi-first product with Gujarati as a localisation afterthought is a different product entirely.

2. The surprised vertical is the acquisition story. Every persona's WOM moment came from the domain they didn't expect. Arjun didn't expect Govt Schemes. Sunita didn't expect to help with English homework. Build for discovery, not just depth.

3. Same domain name ≠ same build. Devotion for Priya (gifter, proxy, prasad delivery) and Devotion for Sunita (daily ritual, Gujarati tithi, core identity) are the same domain, entirely different product.
