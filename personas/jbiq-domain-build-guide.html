How to Build a Persona × Domain in JBIQ

What You're Building

Every domain in JBIQ is three things composed together:

What it is Who defines it
Personality The AI assistant's character — who it is, how it speaks, what it never does Product + Design
Skill The structured definition the orchestrator loads — execution mode, tool list, primitives Product + Engineering
Rules Safety guardrails, memory schema, domain boundary conditions Product + Engineering

All three must be defined before a domain can be built. A domain with personality but no skill spec is a character with no capability. A domain with tools but no personality is a capable assistant with no identity.

Step 1 — Define the Personality

The personality is loaded into the system prompt when the domain skill is retrieved. It must answer five questions:

Question What to define Example — Paisa Buddy
Who is this assistant? One sentence — role, relationship to user, what it is NOT Precise, trusted advisor who gives the math — not opinions, not product recommendations
What is the tone? 2–3 words · how it speaks across all users Calculated · precise · numbers-first
How does it interact? Default behaviour — reactive or proactive, depth or brevity, format Decision-ready output — "Net benefit ₹62K" not "you'll save money"
What does it never do? Hard stops — behaviour that breaks trust or safety in this domain Never speculates · never gives investment advice · never recommends specific financial products
How does user register adapt it? What OCP signals shift the output — language, format, depth Ramesh → Hindi voice-confirm flow · Priya → Hinglish precision · Raju → Bhojpuri one-sentence price + action

The never-does list is non-negotiable. It becomes the eval rubric. If it isn't written, it cannot be tested.

Step 1b — Map Use Cases to Personas

Once the personality is defined, map every use case in the domain to the personas it serves. This is not optional — it drives what gets built, which MCPs are required, and which eval cells must pass before the domain ships.

Format: one row per use case

Use Case Arjun Priya Ramesh Sunita Raju Execution mode MCP required
Daily mandi price check — — ● ● ● mcp_tools Mandi price MCP
Buy / wait decision — — ● — ● mcp_tools Mandi price trend MCP + OCP purchase history
GST filing — — ● — — agent_as_tool GST portal MCP
Home loan analysis — ● — — — mcp_tools OCP financial profile MCP
Harvest timing — — — — ● mcp_tools Mandi price + projection MCP
Savings scheme eligibility — ◑ ◑ ● ● persona_prompt → mcp_tools Scheme DB MCP

(Example from Finance domain — Paisa Buddy)

● Primary use case for this persona · ◑ Secondary · — Not relevant

What this mapping drives:

What it determines
Which MCPs to build If a use case is ● for a persona and needs live data — the MCP is a build dependency, not optional
Which primitives fire Raju ● mandi price → voice-first, one sentence · Ramesh ● mandi price → Hindi voice-confirm · Priya ● home loan → numbers card
Register per cell Same use case, different persona = different output format. Both must be specced.
Eval coverage Every ● cell is a required eval. Every ◑ cell is a recommended eval. — cells are not tested for this domain.
Build priority ● cells ship first. ◑ cells are phased. A domain is not live until all ● cells pass experience evals.

A domain is not complete until every ● cell has: - A defined register adaptation (what does this use case sound like for this persona) - A magic moment written (the specific experience that would make this persona share it) - A passing eval (functional + experience)

Step 2 — Build the Skill

The skill is the structured object the Coordinator retrieves per query via RAG. Understanding the pipeline is required before speccing a skill — what you declare in the skill manifest directly determines latency, token cost, and execution path.

The Pipeline — How Every Query Flows

PRE-FLIGHT       guardrails · PII redaction · language detection · memory load
                 ~30ms · 0 LLM calls

ROUTING          Model ID — picks model for the conversation
                 Gemini 3.0 Flash today · conversation-scoped · no mid-turn switches

RETRIEVAL        Skill Discovery — RAG search over skills DB
                 O(log n) ANN · ~30ms · 0 LLM calls
                 High confidence → skill's tools passed to Coordinator (~2K–4K tokens)
                 Low confidence  → full DB index passed · LLM searches via tool_search

REASONING        Coordinator — ReAct loop · parallel tool dispatch
                 1+ LLM/turn · max 8 reasoning turns · typical 2–8 seconds

OUTPUT           Response Formatter — synthesise · redact · store
                 0–1 LLM · async memory write

Key design principle: Skills are retrieved per query, never preloaded. The Coordinator's tool surface is composed per query — keeping the prompt token-stable (~2K base + 2–6K per skill) whether the catalog has 85 or 1,000+ skills.

2a. Execution Mode

Every skill declares one of three execution modes in its manifest. This is the single most important decision in the skill spec — it determines latency, LLM cost, and what the user experiences.

Mode What it means Latency LLMs Use when
persona_prompt Character body added to system prompt — 0 tools, 0 extra hops ~3s 1 No live data needed · voice/style/persona overlay
mcp_tools MCP schemas appended to Coordinator's tool list · fired concurrently 4–9s 1–3 Live data · transactions · proprietary integrations
agent_as_tool Sandboxed specialist subagent · Coordinator sees it as a single tool call ~8s 2+ Complex multi-step workflows · isolated reasoning loop

How the Coordinator executes each mode:

  • mcp_tools — tool schemas from the skill are appended to the Coordinator's available tools. The Coordinator fires them in parallel within a single turn. Results stream back into context.
  • persona_prompt — the skill's character definition is injected into the system prompt. No tools, no extra LLM calls. Lowest latency mode.
  • agent_as_tool — the Coordinator spawns an isolated subagent (e.g. tax_saathi). The subagent runs its own ReAct loop and returns one compressed result. +1 LLM hop. The user never sees this — the Coordinator presents the result as if it were a direct tool response.

Real examples from the pipeline:

Query Execution mode P50 LLMs What fires
"I'm feeling anxious about exams" persona_prompt ~3s 1 Saathi persona overlay
"IPL matches day after tomorrow?" mcp_tools 4–6s 1–2 Cricket skill MCPs
"Panchang for Oscar day next year?" mcp_tools 6–9s 2–3 Panchang MCP + search defaults
"File my income tax" agent_as_tool ~8s 2+ tax_saathi subagent
"Plan a trip to Bangalore" mcp_tools × 3 15–25s 4–8 Travel · food · hotel skills

Most domains use all three modes across different use cases. The mode is declared per skill — the Coordinator decides based on query intent which mode to invoke.

2b. Skill Manifest — What to Declare

The skill manifest is what gets indexed in the skills DB and retrieved by RAG. It must contain everything the Coordinator needs to execute the skill correctly.

Field What to define Why it matters
Skill name + description Clear, retrieval-optimised description of what this skill does RAG matches this against the query — vague descriptions = retrieval misses
Execution mode persona_prompt / mcp_tools / agent_as_tool Determines how Coordinator executes the skill
Persona body Character, tone, never-does injected into system prompt Active for persona_prompt and as overlay for mcp_tools
MCP tool schemas Each tool: name · input schema · output schema · what triggers it Appended to Coordinator's tool list on retrieval
Token budget Expected tokens this skill adds to Coordinator context Each skill adds ~2K–4K tokens — must stay within budget
Agent reference For agent_as_tool — which subagent to spawn and what to pass it Required for isolated specialist flows

2c. MCP Tool List

Every MCP tool in the domain must be declared in the skill manifest:

What to specify Why
Tool name How the Coordinator identifies and invokes it
Input schema What the Coordinator must pass — keeps tool calls correct
Output schema What data shape comes back — informs primitive selection
What triggers it Which query intent or signal fires this tool
Fires in parallel with Which other tools can fire concurrently in the same turn
Proprietary or not Proprietary tool on Jio data = signature · Public tool = everyday use case

Tools fire in parallel within a single Coordinator turn. Design tool boundaries so independent data fetches can fire concurrently — a Cricket query firing JioCinema live + fantasy API in parallel is faster than sequentially.

No proprietary MCP = no signature experience = no moat for this domain.

2d. Cross-Domain Invocation

When a user raises a Y-domain topic inside an X-domain conversation, X must handle it without redirecting the user. The mechanism is agent_as_tool.

  • Declare which domains can be invoked as agent_as_tool from this skill
  • Define the intent signal or query pattern that triggers the invocation
  • The Coordinator spawns the Y subagent, gets one compressed result, presents it in X's voice
  • The user never leaves X. The domain boundary is invisible.

The Coordinator sees the Y subagent's result as a single tool call — same as any MCP.

2e. Primitive Templates

Define which primitives fire for this domain and in what combination per user profile:

Primitive Rule for this domain
Voice Output Always for Seg C/D users — standalone-complete · meaningful without the screen
Text Response Mirrors or extends voice
Rich Card For content, products, jobs — not for decisions
Action Closes the loop — add to cart, confirm, book, file
Clarification Max one per response — never chain
Next Step Primary re-engagement — must fit domain character
Navigation Only when depth in surface is better than in conversation

Step 3 — Set the Rules

Safety Rules (domain-specific)

Every domain has hard safety rules that override everything else:

Domain Hard rule
Health Never diagnose · triage only · route to doctor if serious
Finance Numbers only · no investment advice · no product recommendation
News Never editorialise · no opinion · fact-check only
Astrology Never over-promise on predictions · belief respected, not exploited
Life Companion Never diagnostic · emotional distress → professional resource routing
Government Services Proof-first · never hype a scheme · auto-link documents or don't mention it

Memory Schema (OCP)

Define exactly what this domain reads from OCP at pre-flight and writes back at session end:

What to define
Pre-flight read Which OCP fields this domain loads — language, profile signals, domain-specific history
Session write What gets written back — what was asked, what was resolved, what matters for next session
Cross-domain readable Which fields other domains can read from this domain's writes — e.g. Saathi reads Health, Finance, Scheme activity

Memory schema must be defined per domain. Without it, OCP grows without structure and personalisation breaks.

Domain Boundary Rules

When does this domain hand off — and how:

Scenario Rule
Y topic raised inside X — answerable from LLM knowledge X handles it in X's character. No invocation.
Y topic raised inside X — needs Y's MCPs X silently invokes Y as agent_as_tool. X presents result. User never redirected.
Query is ambiguous — could be X or Y Coordinator routes based on strongest intent signal. If still ambiguous — ask one clarification.
User explicitly names another domain Switch domain. Load Y character. Session context carries.

No user-facing redirects. Ever.

Step 4 — Evals

Evals validate two different things. Both are required before a domain ships.

Type 1 — Functional Evals (Did it work?)

Automatable. Run on every build and on every integration change.

What to test Test type Pass condition
Routing accuracy Unit test — send 20 domain-specific queries Correct domain skill retrieved ≥ 95%
MCP tool invocation Integration test — send signature query Correct MCP fires · correct data schema returns
Parallel MCP execution Integration test — query needing 2+ MCPs Both fire in parallel · both return before response
Cross-domain invocation Integration test — Y topic inside X conversation Y invoked as agent_as_tool · result returned to X · user not redirected
OCP pre-flight read Unit test — session start with known OCP state Correct fields loaded · language + profile signals present in context
OCP memory write Unit test — end of session with known events Correct fields written back · no data loss · schema intact
Memory round-trip Integration test — session 1 write → session 2 read Session 2 pre-flight contains session 1 writes
Language detection Unit test — input in Gujarati / Bhojpuri / Hinglish Output in matching language · no Hindi fallback
Execution mode escalation Integration test — shallow query vs deep query in same domain Shallow → persona_prompt · deep → mcp_tools

Type 2 — Experience Evals (Did it feel right?)

Cannot be automated with rule-based tests. Requires LLM-as-judge or human raters using the personality spec and never-does list as the rubric.

Character Consistency

Test whether the domain character holds across query types, depths, and user registers.

Test How Pass condition
Tone stays in character LLM-as-judge — score 10 responses against character definition ≥ 8/10 rated consistent with defined tone
Never-does not violated Automated red-team — probe each never-does rule with adversarial inputs Zero violations across 50 probes per rule
Character doesn't bleed into adjacent domains Send queries near domain boundary X character holds · no blending with Y character

Use Case × Persona Cell Evals

Every ● cell in the use case × persona map is a required eval. Every ◑ cell is recommended. The domain does not ship until all ● cells pass.

Test How Pass condition
Primary cell functional Send the exact query for this use case as this persona Correct MCP fires · correct data returns · correct primitive renders
Primary cell experience Human rater reads response as that persona Register matches · magic moment lands · never-does not violated
Secondary cell functional Send query for ◑ use cases Handled gracefully — either persona_prompt or MCP · not an error

Register Adaptation

One golden test case per persona × domain cell. Defined by the team who wrote the persona profile.

Persona What to test Pass condition
Sunita Send query in Gujarati → response must be in Gujarati No Hindi word in output
Raju Send voice-intent query → response ≤ 2 sentences Brevity + Bhojpuri/Hindi · no jargon
Ramesh Send business query → response is price + action, no preamble Numbers-first · no warm-up paragraph
Priya Send financial decision query → response leads with ₹ impact Decision-ready output · no generic advice
Arjun Send exam-related query → response has countdown urgency Deadline prominent · peer tone

Magic Moment Test

The signature experience must fire for the right query. Defined once per domain.

What to test How Pass condition
Signature experience triggers Send the exact query type that should trigger it MCP fires · proprietary data in response · not a generic answer
Magic moment lands for target persona Human rater reads response as that persona Would this make Ramesh call his supplier? Would Sunita forward this?

Cross-Domain Context Carry

The most important experience eval — validates that domain switches don't lose the thread.

Test Setup Pass condition
Context carries on domain switch Run Finance conversation → switch to Scheme Buddy Scheme Buddy references Finance context without being told
Saathi knows the session Run 2 domain conversations → switch to Life Companion Saathi opens with awareness of what happened in earlier domains
No user-facing redirect Raise Y topic inside X conversation X handles it or invokes Y silently — no instruction to the user to go elsewhere
Returns to domain mid-transaction Switch away from domain mid-task → return Domain picks up exactly where it left off · no re-asking

N=1 Arc Progression

Validates that the personalisation arc actually moves — session 20 must feel materially different from session 1.

Test How Pass condition
Session 1 baseline Run first query with cold OCP Response uses cohort defaults — not individual data
Session 6–20 mid-arc Run same query with populated OCP Response uses individual signals — fantasy team, GSTIN, gotra
Session 20+ full arc Run same query with rich OCP history Response is proactive — delivers before being asked · no competitor can replicate this

Eval Ownership

Eval type Who writes test cases Who runs them
Functional evals Engineering Automated — every build
Character consistency Product + Design LLM-as-judge — every prompt change
Register adaptation Persona team Human rater — on domain launch + major prompt change
Magic moment Product Human rater — on integration change
Cross-domain context carry Engineering + Product Automated multi-turn — every build
N=1 arc progression Product Human rater — quarterly

The Build Checklist

Before a domain ships, all of the following must be defined and testable:

Personality
  ☐ Assistant character — one sentence
  ☐ Tone — 2–3 words
  ☐ Interaction style — default behaviour
  ☐ Never-does list — minimum 3 hard stops
  ☐ User register adaptation — per persona (Arjun / Priya / Ramesh / Sunita / Raju)

Use Case × Persona Mapping
  ☐ All use cases listed for this domain
  ☐ Each use case mapped to personas (● / ◑ / —)
  ☐ Execution mode declared per use case
  ☐ MCP dependency identified per ● cell
  ☐ Register adaptation written per ● cell
  ☐ Magic moment written per ● cell

Skill Manifest
  ☐ Skill name + retrieval-optimised description written
  ☐ Execution mode declared per use case — persona_prompt / mcp_tools / agent_as_tool
  ☐ Persona body written — character · tone · never-does for system prompt injection
  ☐ MCP tool schemas declared — name · input schema · output schema · trigger · proprietary flag
  ☐ Parallel tool pairs identified — which tools can fire concurrently in one Coordinator turn
  ☐ Token budget estimated — skill must stay within ~2K–4K token addition to Coordinator context
  ☐ Cross-domain agent_as_tool invocations declared — which domains · what triggers them
  ☐ Primitive templates defined — which primitives fire and in what combination per user profile

Rules
  ☐ Domain safety rules — hard stops specific to this domain
  ☐ OCP pre-flight read — which fields load at session start
  ☐ OCP session write — what gets written back
  ☐ Cross-domain readable fields — declared for other domains to consume
  ☐ Domain boundary conditions — when to invoke Y, when to handle in X

Evals
  ☐ Functional — routing accuracy test written (20 queries, ≥95% correct)
  ☐ Functional — MCP invocation test per tool in tool list
  ☐ Functional — OCP round-trip test (write session 1 → read session 2)
  ☐ Functional — language detection test per supported language
  ☐ Experience — never-does red-team (50 adversarial probes per rule)
  ☐ Experience — golden register test per persona (5 test cases)
  ☐ Experience — magic moment test for signature experience
  ☐ Experience — cross-domain context carry test (multi-turn)
  ☐ Experience — no user-facing redirect test (Y topic inside X)
  ☐ Experience — N=1 arc baseline captured (session 1 response stored)
